# AI scene builder + MP4 export: design contract

The user's vision: **a physics-true "video generator" and sandbox.** You describe a scenario in words and/or give reference images; the app builds it from the real catalog (113 items with true sizes, masses and materials), says plainly which requested things are not in the library (and what it substituted), places everything precisely, runs the validated engine, refines until it matches (and until stated outcomes like "the ball lands in the cup" actually happen), and exports the finished scene as an MP4. Follow-up chat edits the current scene. Quality bar: "do it as perfect as possible … make no mistakes."

Everything below is the contract between the parts. Agents building one part must not change another part's contract without saying so in their report.

## Ground truth you must respect
- Scene format: `web/CONTRACT.md` (scene `{version:2, name, seconds, release, stage, items:[{id,type,x,y,angle(deg),props,held,fixed,name}], goals}`; item anchors differ per type — never assume; derive outlines from the catalog previews / `web/sim` layout).
- Physics: rigid bodies, springs, ropes, pins/hinges, wheels, pulleys, conveyors, motors; **all motion is in one vertical plane** (x along the table, y up); depth (z) is only for looks and mass. No fluids, cloth, soft bodies, people or animals unless the catalog has an item for it.
- The catalog (113 types, props with min/max/defaults/units, materials, tags, descriptions): `GET /api/catalog` (server) or `catalog()` from `web/sim/index.js` (browser). The app's backend switch: `?engine=browser|server` (default server on localhost, browser elsewhere).
- The key: `~/.config/truefoundry/env` (exports `TRUEFOUNDRY_API_KEY`, `TRUEFOUNDRY_BASE_URL=https://tfy.promptlens.trilogy.com/v1`, OpenAI-compatible). **Never** print, log, commit, or send the key to the browser; never put it under `web/`. Server-side code loads it; the local server spawns AI code with `zsh -c 'source ~/.config/truefoundry/env && exec node ai/cli.mjs'`.
- Available models: `ai/research/gateway-models.json` (641 ids; route prefixes like `claude-group/`, `anthropic-primary/`, `gemini-group/`, `openai-group/`, `aws-bedrock/`, `xai-group/`).

## Architecture
```
browser (web/ai/)                                  server (ai/)  — local: web/server.py → node ai/cli.mjs ; Vercel: api/ai/[step].mjs
 panel.js      UI: prompt, images, progress,       core.mjs       callModel(step, messages) with routing (ai/models.json), retries,
               report, follow-up chat                             fallbacks, timeouts, JSON-schema validation + one repair retry
 orchestrator  observe → plan → solve → simulate   prompts/*.md   one prompt per step (versioned)
               → (render → refine)* → tune → apply  schemas.mjs    JSON schemas of every step's output
 solver.js     plan → exact scene (deterministic)  catalog-digest.mjs compact catalog text for prompts (from web/sim catalog())
 shot.js       renders the scene for critique      models.json    step → {model, fallbacks[], params, timeoutMs}
                                                   bench/         eval cases, images, scoring, benchmark runner, results
```
Endpoints (POST JSON; same on local server and Vercel): `/api/ai/observe`, `/api/ai/plan`, `/api/ai/refine`, `/api/ai/edit`. Request `{payload, client:{requestId}}`, response `{ok:true, result, model, ms, usage}` or `{ok:false, error, retryable}`. Bodies ≤ 12 MB (≤ 4 images, each downscaled client-side to ≤ 1536 px JPEG q≈0.85). Every endpoint validates input, never echoes secrets, and only runs its own fixed prompt (no free-form proxying of the key).

## Steps
1. **observe** (only when images are attached; vision). In: images + the user's text. Out (`schemas.observation`): objects `[{label, count, bbox:[x0,y0,x1,y1] in 0..1 image coords, est_size_m:{w,h}|null, material, color, state:"resting|leaning|held|moving|hanging", supports:"label of what it rests on"|null}]`, `relations` (left_of, on, inside, touching, leaning_on, hanging_from…), `motion_story` (what should happen, in order), `view` (camera: side/front/three-quarter/top; which image axis maps to the motion plane), `scale_hint` (a recognisable object with known size), `uncertain[]`.
2. **plan** (text reasoning, catalog-constrained). In: the user's text + observation (if any) + the catalog digest + the current scene (edit mode). Out (`schemas.plan`):
   - `items: [{id, type (MUST be a catalog type), name, props (only real prop keys, within min/max), place, held?, fixed?, why}]`
   - `place` (semantic; the solver makes it exact): `{on: "table"|<id>|"air", x?: m, left_of?|right_of?: {id, gap_m}, angle_deg?, lean?: {from: {on, x}, to: {on, x}}, inside?: <container id>, y_m? (air only), align?: "touching"|"gap"}`
   - `missing: [{asked, reason, substitute_type|null}]` — every requested thing that is not in the library MUST appear here, honestly; never silently swap.
   - `goals: [{kind, label, ...}]` (every outcome the request states or the picture shows; kinds in `ai/goals.mjs`: `in {item, container}`, `falls {item | items}`, `hits {item, target, before_s?}`, `moves {item, min_m}` — **(added)**), `tune: [{id, param: "x"|"y"|"angle"|<prop>, min, max}]` (knobs the tuner may move to make goals happen), `seconds`, `title`, `notes`, `differences` (what differs from the picture or request and why) and, with an observation, `covers` (every observed object → the items that build it) **(added)**.
3. **solve** (deterministic, browser, `web/ai/solver.js`). Plan → scene: resolves each item's outline from the catalog preview / `web/sim` layout for its props; puts it on its support (the table top or the top surface of the support item at that x, after that item is placed), applies left_of/right_of gaps and `touching`, computes lean angles from the two support heights, keeps items inside the stage, separates overlaps (minimal moves, never through a support), honours held/fixed, then checks with `web/sim` overlaps → zero overlap warnings is the target. Topological order of supports; cycles are an error reported back. Pure function, unit-tested in node.
4. **simulate**: the app's normal path (`/api/simulate` or the browser engine) → summary (events, goals, warnings).
5. **refine** (vision when a reference image or a render is involved; loop ≤ 3). In: request, plan, solved scene digest (items, positions, outlines' bounding boxes), sim summary (events, goals ok/failed, warnings), the render(s) of the solved scene (Wide camera, plus a close-up if useful) and the reference image(s). Out (`schemas.refine`): `{done, score_0_10, issues[], patches:[{op:"move|set_props|add|remove|replace_type|set_place", id, …}]}`. The orchestrator applies patches by editing the plan and re-solving (never by raw coordinates unless `set_place` with x/y).
6. **tune** (deterministic, browser): when goals fail and `tune` knobs exist, a bounded search (coarse grid then golden-section/Nelder-Mead, ≤ 40 engine runs, ≤ 20 s) over the knobs; keeps the best; reports what it changed.
7. **edit** (follow-up chat): In: current scene + digest + instruction (+ optional images). Out: same as plan but as a diff (`patches`) when small, or a whole plan when the user asks for a different scene.
8. **apply**: the final scene goes through the app's normal `setScene` as ONE undoable step, named after the plan title; the report (used items, missing + substitutions, assumptions, goal results, what refine/tune changed) is shown in the AI panel and kept in history.

## Model routing (`ai/models.json`)
Per step: `{model, fallbacks:[…], params:{temperature, max_tokens, reasoning_effort?, response_format?}, timeoutMs, needsVision}`. Chosen by the benchmark in `ai/bench/` (research + gateway probes + measured quality/latency on the eval set). Speed matters most for edit and the refine loop; quality matters most for observe and plan. The table, scores and the reasoning behind each pick go in `ai/research/benchmark.md`.

## UI (AI panel)
A "Build with AI" button in the top bar opens a panel (desktop: a right-side drawer; phone: bottom sheet) with: a prompt box (Enter to build, Shift+Enter newline), image attach (button, drag & drop onto the panel or the view, paste), thumbnails with remove, a mode hint (new scene vs edit current), live step progress (Looking at your images → Planning → Placing → Simulating → Refining 1/3 → Tuning → Done) with elapsed time and Cancel, then the report and a chat for follow-ups. Errors are plain and recoverable (gateway down, timeout, invalid output after repair, nothing buildable). The result applies as one undo step; "Undo AI build" is just ⌘Z. Works in both backends. Keyboard: `A` opens the panel (when not typing).

## MP4 export (separate build; see ai/EXPORT.md when written)
Deterministic frame-by-frame rendering of the current scene at a chosen resolution (720p/1080p/1440p/4K) and fps (30/60), camera (Wide/Follow/Orbit path), forced high quality, encoded in the browser with WebCodecs H.264 + an MP4 muxer (vendored, pinned), progress + cancel, download as `<scene>.mp4`. Optional impact sounds synthesised from the engine's impact log (material, speed) mixed with OfflineAudioContext and muxed as AAC. Fallback when WebCodecs is missing: MediaRecorder (real-time). Verified with ffprobe (codec, size, fps, frame count, duration) and frame comparison against the live view.

## Server AI core (built 2026-10-15: `ai/core.mjs`, `schemas.mjs`, `catalog-digest.mjs`, `scene-digest.mjs`, `steps.mjs`, `cli.mjs`, `models.json`, `prompts/`, `test/`; `web/server.py` routes; `api/ai/[step].mjs`)
These lines make the contract above exact. Where they add to it, they are marked **(added)**.

**Calling a step.** `POST /api/ai/<observe|plan|refine|edit>` with `{payload, client?: {requestId}}`. Answer `200 {ok: true, result, model, servedModel, ms, usage, attempts, warnings, prompt, catalog?, requestId?, goals? (refine: the plan's goals checked, below)}` or `{ok: false, error (plain words), code, retryable, attempts?, details?}` with status 400 `bad_input` (the error says which field), 404 (unknown step), 413 `too_large`, 429 `busy` (retryable, with `Retry-After`, `position` and `retryAfterMs`: **(changed again, §13.1)** the local server runs 12 steps at once and at most 4 observe / 6 plan / 8 refine / 8 edit of them, and queues the rest first come, first served for up to 90 s before it answers busy), 403 / 415 (not this app: §13.1), 502 `gateway` / `invalid_output` (the models failed, or answered unusably even after the repair; `details` lists the validation errors), 504 `timeout` / `budget` (retryable). **(added)** `GET /api/ai/progress?id=<requestId>` → `{ok, id, state: "waiting"|"running"|"done", step, position? (in the queue), model?, attempt?, repair?, phase?: "thinking"|"writing", tokens? (≈ thought + written so far), ms?, elapsed_ms, age_ms}` (404 when unknown); `GET /api/ai/progress` → `{ok, running, waiting, slots}`. Numbers and model names only; the client polls it to show "Waiting for a free AI slot (2nd)" or "Still thinking: 1,200 tokens". A client that hangs up cancels its step (the server stops the process; the gateway call is dropped). `usage` sums every attempt (`prompt_tokens`, `completion_tokens`, `cache_read_input_tokens`, `costInUSD`...). `warnings` lists small slips the validator fixed by itself (e.g. `place.angle` read as `angle_deg`).

**Payloads.** Pictures are data URLs (`data:image/jpeg|png|webp|gif;base64,...`) or `{data, label?}`; at most 4 per field; no remote URLs.
- `observe {text?, images*}`.
- `plan {text* (or observation), observation?, scene? (the current scene, when the request changes it), images? (reference pictures)}`. The plan always describes the WHOLE scene.
- `refine {text, plan*, scene* (the solved scene), sim? ({summary, warnings} of its run, as /api/simulate gives them; optional `final: [{id, x, y}]`, `tuned`), renders? (pictures of the solved scene, `label` e.g. "wide"/"close-up"), images? (reference pictures), round? (1-based), rounds? (the most there will be), observation? (the observe step's answer: the critic's checklist; `plan.covers` carries the same counts and sizes) **(added)**}`. **(added)** The server checks every goal of the plan itself: `in` from `sim.summary`, the other kinds on its own run of the solved scene (web/sim + the engine bundle, the same run as /api/simulate, ~0.2 s), and shows the critic MET / FAILED with numbers ("5 of 7 fell", "7 of 10 fell": counted per rigid body (a weld group: a bowling pin's six parts are one; hinged parts and a car's wheels are left out), each fallen when it turned past its own tipping angle, atan(base/height) of its outline at the start + 5° within 20…85°, or was knocked down at least half its smaller side (not a body on wheels: driving down a ramp is no fall)); the answer's top-level `goals` carries those results (`ai/goals.mjs` `checkGoals`).
- `edit {text*, scene* (the current scene), plan? (its plan, when it has one), history? ([{role: "user"|"assistant", text}], ≤ 20), images?}`.
The server reads every scene through `web/sim` `clean()` (the builder's own checks: a bad scene is a 400) and gives the model a digest of it built by `web/sim` `layout()`: every item's anchor, angle, true outline box (world metres), what it rests on, overlaps.

**Coordinates (binding for prompts, solver and refine).** Metres, the scene's own frame: `x` is the scene's x (NOT offset from the stage's left edge; the default table top runs x −0.55…3.15, the stage −0.56…3.19), `y` up from the table top (**the table top is y = 0**), angles in degrees counter-clockwise. `place.x` and `place.y_m` are the item's **anchor** (the same point as the scene item's x, y; the catalog says per type where it is), so an x read from the current scene can be given back as is.

**Plan** (`schemas.planSchema`): `{title*, seconds* (0.5–20), release? (0–20, default 0.5), items* (1–150), missing*, goals*, tune*, notes*, assumptions?, table? {props} (added: the table's own props, e.g. a longer or steel table), stage? {x0,x1,y0,y1} (added)}`. Item: `{id* (1–40 of [A-Za-z0-9_-], unique; "table" and "air" are reserved: "table" always means the scene's table, which plans never list), type* (a catalog key, never "table"), name?, props? (only the type's keys, inside min/max; choices from its list; ints whole), place*, held?, fixed?, why?}`. `held`/`fixed` on a static type are dropped (warning); both true is an error. Goals: `{label, item, container}` where the container's type is `box`, `cup`, `bucket` or `basket` (the only ones `inside()` checks) and the item is dynamic and not fixed; the validator adds `kind: "in"`. Tune: `{id, param: "x"|"y"|"angle"|<a number prop of that type>, min < max (inside the prop's range), why?}`. Missing: `{asked, reason, substitute_type (catalog key or null), substitute_id? (the plan item standing in)}`.

**`place` semantics for the solver** (prompts/_place.md says the same to the model):
- `on`: `"table"` | an item id (rest on its top surface at x) | `"air"` (**exact**: the anchor goes exactly to (x, y_m); a dynamic item falls from there unless held/fixed). Optional when `lean` is given (then it is `"air"`).
- `x`: the anchor's x. Missing on an item resting on another item: the middle of that item's top.
- `left_of` / `right_of`: `{id, gap_m}` — the item's outline ends gap_m (edge to edge, horizontally) left/right of the other's outline; **gap_m missing or 0 = touching (added)**. `align: "touching"` forces 0; `"gap"` keeps gap_m. Not together with x.
- `y_m`: air only (required there).
- `angle_deg`: missing = 0, **except an item resting on a tilted surface takes that surface's slope (added)**, so a block or a car sits flat on a ramp.
- `lean`: `{from: {on, x, y?}, to: {on, x, y?}}` — a long straight item from end to end; an end on `"table"` or an item rests on its top at that x; **an end on `"air"` has its height `y` (added)**. The solver sets centre and angle, and — **when the plan leaves the type's `length` prop out — the length that spans the ends (added)**. No x, left_of, right_of or angle_deg with lean.
- `inside`: a container id; the item rests on its floor between its walls; `on` must be the same id; x optional (middle).
- References may not form cycles (the validator reports them); the solver places supports first.

**Patches** (refine and edit; prompts/_patches.md; at most 150 per answer **(changed from 40)**): `move {id | ids, x? | dx?, y_m? | dy? (air items only), angle_deg?}` (`ids`: the same change to several items, **(added)**; the validator expands it into one patch per item, so clients only ever see single patches) (dx on a left_of/right_of item changes its gap; an item without x must get x), `set_props {id | ids, props}` (null = back to default), `add {item}`, `remove {id}` (also drops its goals and knobs), `replace_type {id, type, props?}` (keeps id, name, place; drops props the new type lacks), `set_place {id, place}`, and **(added)** `set_item {id, name?, held?, fixed?}`, `set_scene {seconds?, release?, title?}`, `set_goals {goals}`, `set_tune {tune}`. Every patch may carry `why`. They apply in order to the plan; `schemas.applyPatches(plan, patches, catalog)` is the reference implementation (pure, no dependencies; the validator applies them the same way and reports only problems the patches create). A scene with no plan (made by hand) is edited through `schemas.planFromScene(scene)`: every item `on: "air"` exactly at its anchor and angle, so untouched items stay exactly where they are.

**Refine answer** `{done, score_0_10, issues: [{severity: "high"|"medium"|"low", text, ids?}], patches, notes?}`; `done: true` means "apply as is" and carries no patches. **(added)** While a stated goal fails (and is not an `in` goal its tune knobs can still reach), the score is capped at 7 and `done: true` gets the repair turn; a name stating a number a patch changes ("Row of 12 dominoes" → count 15) gets a `set_item {name}` patch appended. **Edit answer** `{mode: "patch"|"plan", reply (≤ 2 short sentences, for the chat), patches (mode patch; [] = nothing to change, e.g. a question), plan (mode plan, a whole plan), missing, notes?, assumptions? (mode patch: the plan's, rewritten when the change made them untrue), undo? (true: the user asked to go back; no patches; the client may call its own undo)}` **(added)**. In mode patch with patches, `missing` comes back with the plan's earlier entries kept (the client replaces the plan's list with it); names follow changed numbers as for refine. **Observation** `{summary?, objects: [{label (unique), count, image?, bbox [x0,y0,x1,y1] (0..1 from the image's top-left), est_size_m {w,h,d?}|null, material, color, state, supports (a label, an environment word like "table"/"floor"/"hand", or null), notes?}], relations: [{a, rel, b}], motion_story: [text], view: {camera, plane (how the picture maps onto the x-y plane), notes?}, scale_hint: {label, size_m, dimension}|null, uncertain: [text]}`.

**Faithfulness checks (added 2026-10-15).** Some checks are *soft* (`validate(...).soft`): they get the one repair turn when at least min(timeoutMs, 60 s) of the budget is left, but an answer that still has them is used (they become `warnings: "not fixed: ..."`), and a repair that breaks a usable answer falls back to it — so a faithfulness check never costs a build. Soft: plan `covers` must account for every observed object by its exact label (ids, or `ids: []` + a note), with the observed count built (domino rows count their dominoes) unless a note says why; a picture asked to "make it work" whose motion story ends in a container needs an `in` goal; refine may not change the material of a thing the request names (unless the request names the new material: friction and bounce instead); refine `done: true` with a failing goal (see above). The critic's request carries **the reference checklist** (from `plan.covers`, else the observation): each observed object, its count and size as seen, what builds it (true outlines from `scene-digest` rows, which also give each part's size: `parts`), and `COUNT DIFFERS` / `SIZE DIFFERS` (> 25 % by the largest side) only where the comparison is clear, since a false alarm makes the critic break a good scene: several observed objects built by one item are its parts (a ramp and its legs, a pendulum's bob and its stand: no count, and only a part the label names is compared), a group seen one by one is counted in all ("domino 7" is compared with the row's 7th domino), and a thing hung on a stand is also compared with its bob (observe sizes things without their stands). A sketch or drawing (the request or the observation says so) is not to scale: its checklist compares counts, never sizes, and refine.md tells the critic not to resize or retype things to a sketch's proportions. The plan sets the scale deterministically (plan.md): a thing of standard real size when the picture has one, else every catalog item at its default size, changing a size only where the picture clearly differs by more than about 1.5×; it names its anchor in `assumptions`.

**Streaming (added 2026-10-15).** A step with `stream: true` in models.json calls routes whose quirk says `stream: true` (they stream their thinking as it goes: claude-group, the OpenAI group; Bedrock buffers whole answers and is called plainly) with server-sent events: an attempt with no byte for `idleTimeoutMs` (90 s) is dropped as a timeout and the next try or route starts, while a plan that keeps thinking may use its whole `timeoutMs` (plan: 300 s). Progress (`onProgress`) goes to the CLI, which writes `AIPROGRESS {...}` lines on stderr when `AI_PROGRESS=1` (web/server.py sets it and serves them at `/api/ai/progress`).

**Calls, retries, repair (core.mjs).** Per step (models.json): primary route + fallbacks, `params` (no temperature: Opus 5.5 and GPT-6.x reject it), `timeoutMs` per attempt, `budgetMs` for the whole call (the local server stops the process at budgetMs + 15 s), `retries` per route with exponential backoff and Retry-After for 429/5xx/timeouts/network errors; a 400 that names a rejected param drops it and retries at once; a 4xx moves to the next route; a route with `vision: false` is skipped when pictures are sent; Claude routes get the system prompt as a cacheable block (Anthropic prompt caching through the gateway: the catalog digest is read from cache on the next call, ~$0.17 → ~$0.007). Output: JSON extracted (fences, prose, trailing commas tolerated), validated, and ONE repair turn that shows the model its exact errors (structural and semantic together); still invalid → the next route while the budget lasts. The key is only read from `process.env`, never logged, and scrubbed from every error and answer.

**Prompts.** `prompts/{observe,plan,refine,edit}.md` with `{{include:_world.md}}`, `_place.md`, `_plan_format.md`, `_patches.md` (shared rules, edit once) and `{{CATALOG}}` (full digest) / `{{CATALOG_BRIEF}}` (one line per type; refine gets full detail only for the types in its scene). The system prompt is static per step and catalog version (cacheable); everything per request goes in the user turn. `out.prompt.system` is a hash of the system prompt, for the benchmark.

**Catalog digest.** From `web/sim` `catalog()` (else the local server's /api/catalog, else the last good digest on disk), cached in `ai/.cache/catalog-digest.json` keyed by the web/sim files (`AI_CACHE_DIR` moves it). Per type: key, name, category, static/dynamic (and "on a fixed frame or pivot"), description, facts, mass, anchor, outline relative to the anchor at defaults, own props (unit, default, range, choices, auto), surface material and contact numbers, joints/motors/belts/air, goal-container or not, release-driven, tags, plus verified planner notes (which way a fan blows, a pendulum's start_angle sign...). Measured 2026-10-15: 71.9k characters = 34.6k Opus 5.5 tokens (24.4k GPT-6.1); the brief list 10.3k characters = 5.5k tokens.

**Measured on the gateway (live smoke, 2026-10-15, Opus 5.5 on claude-group):** observe 21–32 s, plan 9–108 s (typical 20–45 s; reasoning_effort high), refine 9 s, edit 13–15 s (reasoning_effort low). Every step answered; 3 of 15 first answers needed the one repair and all were repaired (the one whose reason was recorded put `align` inside `right_of`, which the validator now fixes by itself).

**Tests.** `npm run test:ai` (`node --test "ai/test/*.test.mjs"`, ~5 s, a mock gateway on 127.0.0.1: retries, fallback, param stripping, timeouts, budget, abort, repair, extraction, no key in any output; the validators against the real catalog; the CLI's exit codes and SIGTERM; web/server.py's route through its real `zsh -c 'source ~/.config/truefoundry/env && ...'` command with HOME pointing at a fake env file; the Vercel twin). `npm run smoke:ai` runs every step once through the real gateway and writes the answers to `ai/research/live-smoke.json`.

## Protecting the hosted endpoint (before ANY public deploy of `api/ai/[step].mjs`)
**(Superseded in part by §13.7, which builds (1), (3) and (5) into the twin (access and origin fail closed, the time cap) and adds a per-instance queue. (2), a whole-site rate limit and a daily spend cap, is still to set up: a Vercel Firewall rate-limit rule or a KV counter.)**
The Vercel twin is not deployed. It spends the AI key on every request, so before it is reachable from the internet it needs: (1) authentication — Vercel Authentication / deployment protection, or a signed session cookie checked in the handler (the browser never holds the key either way); (2) a per-user and per-IP rate limit and a daily spend cap (Vercel Firewall rate-limit rules, or a KV counter checked before `runStep`; `usage.costInUSD` in every answer says what each call cost); (3) `ALLOWED_ORIGINS` set to the site's origin; (4) the key only in the project's encrypted environment variables (`TRUEFOUNDRY_API_KEY`, `TRUEFOUNDRY_BASE_URL`), never in the repo or the client bundle; (5) `functions["api/ai/[step].mjs"]` in vercel.json with `maxDuration` ≥ 300 and `includeFiles` for `ai/prompts/**` and `ai/models.json` (read at run time), and `AI_CACHE_DIR=/tmp`. Note Vercel caps request bodies at about 4.5 MB: the hosted client must send smaller pictures (or upload them to Blob first) than the local server's 12 MB.

## 13. Round 2 contracts (2026-10-15, evening): the queue, stages, the rate-only check, speed, the hosted endpoint
Server side done in `ai/**`, `api/ai/[step].mjs` and `web/server.py`'s AI routes; everything marked **browser** is for `web/ai/` (and `web/app.js`'s `api()`), which this round did not touch. ### 13.1 The AI queue on the local server (`web/server.py`)
- **Limits** (env overrides in brackets): 12 steps run at once in all [`AI_SLOTS`], and at most observe 4, plan 6, refine 8 (a rate-only check counts as refine), edit 8 of them [`AI_STEP_SLOTS="plan=6,edit=8"`]. Long plans and picture looks can no longer take every slot from quick edits and checks.
- **Order:** first come, first served among the waiting requests *whose step has room* (a plan waiting for a plan slot does not hold up an edit behind it). A request waits up to 90 s [`AI_QUEUE_WAIT`]; at most 48 wait at once [`AI_QUEUE_MAX`].
- **Refused** (the queue is full, or 90 s passed): `429` with `Retry-After: <s>` and `{ok: false, code: "busy", retryable: true, busy: true, position (1 = next), retryAfterMs (an estimate from the step's recent durations, 1–120 s), retryAfter (s), error}`. **browser:** wait `retryAfterMs` (not a fixed backoff) and show the position ("2nd in line for the AI").
- **Progress:** `GET /api/ai/progress?id=<requestId>` while waiting: `{state: "waiting", step, position, eta_ms}`; running: as before. `GET /api/ai/progress`: `{running, waiting, slots, queue_max, steps: {observe|plan|refine|edit: {running, waiting, slots}}}`.
- **Hanging up** leaves the queue at once (checked every 0.25 s); a running step's process is stopped (its gateway call dropped).
- **Only this app may call** `POST /api/ai/*` (before any process starts): `Content-Type: application/json` or `415`; a `Host` of this server (`localhost`, `127.0.0.1` or `[::1]` with its port) or `403`; an `Origin`, when the browser sends one, of this server or `403`. A web page in another tab can no longer make the local server spend the key (a cross-site JSON post needs a preflight this server never grants; a rebound hostname fails the Host check). `web/app.js` `api()` already sends the right headers.

### 13.2 Stages: per-stage expectations, checks and knobs (plan, refine, edit)
- **Plan field** `stages` (optional; plan.md asks for it for a chain of 4 or more stages): `[{label (≤ 120), does? (≤ 300: what the stage must do, with its key number), items? ([ids]), check? (a goal: {kind: in|falls|hits|moves, ...the kind's fields}; its label defaults to "Stage n: <label>"), tune? ([knobs] ≤ 6, the same shape and rules as plan.tune)}]`, ≤ 12 stages, in order.
- **Never a repair:** a stage problem is fixed in place with a warning: unknown fields dropped, `ids`/`expect` read as `items`/`does`, an item id that is not in the plan dropped from `items`, a check that names a missing item or does not fit its kind (`ai/goals.mjs` rules, the same as the plan's goals) dropped, a knob that does not fit or that an earlier stage already has dropped.
- **Every stage knob is also in `plan.tune`** (the validator copies it there, up to 12 knobs), so a tuner that does not know stages still turns it; `stages[i].tune` says which stage owns it.
- **Patches:** `{op: "set_stages", stages}` replaces the list (checked like the plan's); `remove` takes the item out of every stage's `items`, drops a check that names it and its knobs; `replace_type` drops stage knobs on props the new type lacks.
- **Refine checks every stage's check** on the same run as the goals (an `in` check is added to that run's scene goals so the engine checks it) and shows the critic `Stage checks (in order): 1 MET: …; 2 FAILED: … The first stage that fails is stage 2: fix it first …`. Stage checks never cap the score (goals do). The answer carries them: top-level `stages: [{stage (1-based), label, kind, ok: true|false|null, detail}]` (beside `goals`; also in the rate-only answer).
- **browser, the tuner:** when a goal fails and the plan has stages: check every stage (`web/ai/goals.js` `checkGoals` on the run; an `in` check needs `{item, container}` added to the scene's goals for the tuner's runs only, never shown as the user's goal); take the FIRST stage whose check fails and that has knobs; search only its knobs (the same coarse grid + golden section), objective in order: that stage's check, the number of later stage checks met, the goals met, `physics()`; keep its best, freeze those knobs, re-check, go on to the next failing stage while the run budget lasts (40 runs, 20 s in all); finally the knobs no stage owns, for the goals. Without stages, as now.
- **browser, the card:** a stage list under the goals ("Stage 2 · Dominoes fall ✗ 4 of 12 fell"), from the answer's `stages` or the client's own check of the final run.

### 13.3 The rate-only check (refine)
- **Request:** `POST /api/ai/refine` with the same payload as a critique plus `rate_only: true` (anything but a boolean is a 400).
- **Answer:** `result: {score_0_10, issues: [{severity, text, ids?}], notes?, rate_only: true}` — never `done` or `patches` (a model that writes them has them dropped, with a warning); `goals` and `stages` as for a critique. The score is capped at 7 while any stated goal fails (the tuner has had its turn). It runs on `models.json` `"rate"`: Opus 5.5 at effort **low**, 8k max tokens, 60 s per attempt, 120 s budget, the same fallbacks; the same system prompt as a critique, so it reads the prompt cache.
- **browser, use it (1) for the final check** (the version on the table changed after the critic last saw it: its last patches or the tuner): `rate_only: true`, treat `done` as `score ≥ 8`. **(2) Rate before a full critique** in rounds ≥ 2: when the last round's patches made every stated goal pass, nothing floats (solver `floats`/`floats_end`) and the picture's coverage has no gaps, send the round as rate-only first; a score of 8 or more ends the loop (done, no patches), below 8 the full critique runs as before. Half of the second rounds in the repair A/B were confirmations (done, no change) that cost a full critique.

### 13.4 Edits: what the browser's fast path gets
- The edit step itself: p50 4–5 s on the gateway (3.9 s before the chat fields of §13.9, 4.9 s with them: about 200 more output tokens), plus about 0.4 s to start its process (measured: zsh + node + imports + the catalog digest; not worth a process pool).
- **notes/assumptions (mode patch):** `notes` comes back only when the change made the plan's notes untrue (the whole text); `assumptions` comes back as the whole list (the earlier ones still true, word for word, plus the choices this change made: "bigger = 1.5×") when the change chose something or made one untrue. Absent = unchanged: **browser** keeps the plan's, and replaces them when present (as the frozen client does).
- The fast path (apply after one solve + run when nothing broke, critique only on request) is the browser's (built in the frozen client: `report.quick`).
- An edit that the user meant as a different scene: §13.8 (send `intent: "edit"` from "Edit with AI" so such an answer is not planned).

### 13.5 Sketches are observed at lower effort (server side, automatic)
A request that calls the picture a sketch, drawing, diagram, doodle, cartoon or illustration (`steps.mjs` `SKETCH_RE`) is observed with `models.json` `observe.simpleParams` (effort low). On the bench's sketches low effort built as well as medium (4 of 4 at both) in about half the time; photos and the app's own renders stay at medium (low lost pass there: benchmark §5, §12).

### 13.6 Prompt caching for an hour
Routes with the quirk `cacheTtl: "1h"` (claude-group and Bedrock Opus 5.5; both checked through the gateway: a 1-hour entry was read after 7 minutes, a 5-minute one was written again) mark the static system prompt `cache_control: {type: "ephemeral", ttl: "1h"}`; a route that rejects the field is asked again with the default lifetime. The first build after a pause of 5–60 minutes reads the 44k-token catalog prompt from the cache (≈1–2 s sooner to the first token, and no cache write). Effort changes do not break the cache (a low-effort rate-only check read the medium critique's entry).

### 13.7 The hosted endpoint (`api/ai/[step].mjs`, Vercel)
- **Same shapes and checks as the local server**: POST only (405), the four steps (404), `Content-Type: application/json` (415), ≤ 12 MB (413; Vercel stops bodies over 4.5 MB first), `{payload}` (400), the steps' own payload checks.
- **Origin, fail closed on Vercel:** a call must carry an `Origin` that is this deployment's own URL (`VERCEL_URL`, `VERCEL_BRANCH_URL`, `VERCEL_PROJECT_PRODUCTION_URL`) or one in `ALLOWED_ORIGINS` (an alias or a custom domain), and a `Sec-Fetch-Site`, when sent, of `same-origin`; else 403. Off Vercel (tests, local tools) only `ALLOWED_ORIGINS`, when set, is checked.
- **Access, fail closed on Vercel** (401 `unauthorized`; 503 `not_configured` when nothing is set up):
  - *production (and any deployment):* an `ai_session` cookie, `HttpOnly; Secure; SameSite=Strict; Path=/api/ai`, signed with HMAC-SHA256 by `AI_SESSION_SECRET` (≥ 32 characters), valid `AI_SESSION_HOURS` (default 72). It is set by **`GET /api/ai/session?invite=<code>`** (a code from `AI_INVITE_CODES`, comma-separated, each ≥ 12 characters), which answers `303 Location: /`. Nothing secret is in the page or its JS; the page's own same-origin fetches carry the cookie. To show an investor: send the deployment's share link (Vercel's protection) and then the invite link, or the invite link alone where Vercel Authentication is off.
  - *a protected preview only* (`VERCEL_ENV != "production"`): the header `x-ai-access: <AI_ACCESS_TOKEN>` (≥ 16 characters), for scripted checks or a static build that puts the token in the page (acceptable only behind Vercel Authentication; never honoured in production).
  - **Deploy (Vercel prep agent, docs/DEPLOY.md step 5):** add `AI_SESSION_SECRET` (e.g. `openssl rand -base64 48`, as `--sensitive`) and `AI_INVITE_CODES` to Preview (and later Production), then open `https://<deployment>/api/ai/session?invite=<code>` once in the browser that will demo. Without them every AI call answers 503 `not_configured` on Vercel (fail closed). `ALLOWED_ORIGINS` stays unset for plain deployment URLs (they are allowed by `VERCEL_URL`).
- **Time:** `maxDuration` 300 s (Hobby's most with Fluid; `vercel.json` says the same). The step's budget is capped at 280 s minus its wait for a slot (`callModel` `budgetMs`), so a slow plan ends with its own 504 `timeout`/`budget` JSON, never Vercel's.
- **Streaming (browser, opt-in):** with `Accept: application/x-ndjson` the answer is `200`, `Content-Type: application/x-ndjson`, one JSON object per line: `{type: "start", step, requestId?}`, `{type: "progress", model, attempt, repair, phase: "thinking"|"writing", tokens, ms}` (at most one a second), `{type: "heartbeat", ms}` (every 10 s when nothing else was sent: no proxy drops a long silent plan), and last `{type: "result", status (the HTTP status it would have had), ...the usual answer}`. On the hosted page the client should send that header, read lines as they come (progress replaces `GET /api/ai/progress`, which Vercel does not have), and use `result.status` / `result.code` as it uses the status and code today. Without the header: one JSON answer, as before.
- **Concurrency:** one instance runs at most `AI_SLOTS` (12) steps and the same per-step caps; the rest wait first come, first served for `AI_QUEUE_WAIT` (30 s, it counts against maxDuration), ≤ `AI_QUEUE_MAX` (24) waiting; then 429 busy `{busy, position, retryAfterMs}` with `Retry-After`. Instances do not share a queue: the whole site's limit is a Vercel Firewall rate-limit rule on `/api/ai/` (docs/DEPLOY.md), plus the spend cap still to add.

### 13.8 New scene or change? A change to the scene on screen is an edit, never a new scene (`intent`)
The user's report (2026-10-15): with the starter machine on screen, "change the yellow ball to a tennis ball and the red ball to a basketball" built a whole new scene (the client had sent it to the plan step without the scene: "No current scene was given"). The server now decides, and never plans over a scene a request refers to.
- **plan** payload `intent`: `"auto"` (default) or `"new"`. With `"auto"`, a `scene` that has items in it and no `observation`: the edit step (low effort) and a fresh plan start together. If the edit step answers a change (`mode: "patch"`), the fresh plan is dropped and the answer's `result` is the scene's plan (`payload.plan`, else the scene read as a plan: every item at its exact anchor) with the patches applied, plus top-level `intent: "edit"`, `why`, and `edit: {mode, reply, why, patches, missing, notes?, assumptions?, undo?}`: untouched items stay exactly as they were. If it answers `mode: "new"`, the fresh plan is the answer, with `intent: "new"`, `why`, `edit: {mode: "new", reply, why}`. Without a scene with items, with `intent: "new"` or with an `observation` (a build from a picture), the plan step plans the new scene directly. If the decision itself fails, the step fails (retryable): it never falls back to a new scene over the one on screen.
- **edit** answers `mode: "patch" | "new"` (`"plan"` is still accepted) with a one-sentence `why`, and top-level `intent: "edit" | "new"`. Payload `intent`: `"auto"` (default): an answer of mode `"new"` goes on to plan the new scene (the plan step, medium effort, the request alone), and the answer is `{mode: "plan", reply, why, plan, missing}` with top-level `intent: "new"`; `"edit"` (**browser**: the "Edit with AI" path, which never replaces the scene from there): it comes back as it is, `{mode: "new", reply, why, missing: []}`, with no planner call (the client offers "Build it as a new scene", which calls plan with `intent: "new"`); a non-patch answer under `"edit"` gets the one (soft) repair turn first. Anything else is a 400.
- **What the edit prompt asks** (edit.md): every request that names or points at things in the scene, or asks to add, remove, swap, move, resize, retime or "make it work (again)", is a patch, even when it also says "new" or "build" ("New scene: the same machine but with a bowling ball" stays an edit; the reply says the rest was kept). Patches touch only what the request is about plus the fewest others the physics needs (each said in the reply); every other item keeps its id, type, props and place exactly. A kind swap (`replace_type`) keeps id, place and role and re-seats the thing on the same support at the same x (`set_place {on: <support>, x}`) so a bigger or smaller one neither sinks nor floats; a name that says the old kind ("Superball") follows the new one (the validator adds the `set_item`).
- `web/server.py` gives an edit the time budget of an edit plus a plan (the escalation); `ai/cli.mjs` and `api/ai/[step].mjs` pass `intent`, `why` and `edit` through.
- **The user's chosen UI (coordinator, 2026-10-15 evening) makes the intent explicit, and "auto" applies only when no intent is sent:** "Edit with AI" always sends `POST /api/ai/edit {text, scene, plan, history, images, intent: "edit"}` (the scene on screen is changed, never replaced: the request tells the model the user pressed Edit, a non-patch answer gets one repair turn, and a `"new"` answer that stays comes back as `{mode: "new", reply, why}` with no planner call: the client offers "Build it as a new scene"); "New → Build with AI" sends `POST /api/ai/plan {text, observation?, images?, intent: "new"}` with no scene.
- **browser:** (1) send the scene on screen with every request; edit by default when it has things in it. (2) On a plan answer with `intent: "edit"`, take the edit path: apply `edit.patches` to your own base plan (your `planFromScene` with `pinDrifters` keeps untouched items exact), show `edit.reply` and the change list, one undo step; never apply it as a new scene. (3) On an edit answer with `intent: "new"`, apply `result.plan` as a new scene and show `result.reply`. (4) Show `why` in the turn's folded details. (5) Send `sim` with an edit: the run of the scene on screen as for refine (`{summary, warnings, final: [{id, x, y}]}`); the edit model then sees which goals happen now (MET / FAILED, every kind) and where things ended, which "make it work again" needs (without it the model can only guess where the ball lands).
- Measured live on the starter: the report's request through edit 9.6 s and through plan (auto) 12.1 s, both intent edit, every untouched item within 1.5 mm after solving; "a pendulum knocks over ten dominoes" through plan (auto) 13.6 s, intent new; "start over: just a tennis ball rolling down a ramp into a cup" through edit 26.7 s, intent new (the plan step built it). Bench: edit cases d20–d29 (`ai/bench/cases/text.json`; ai/research/benchmark.md §13).
- **browser, as built (ai2-client repair, 2026-10-15 evening; supersedes the browser bullets (1)–(3) above where they differ):** the top bar has **Edit with AI** (A: the drawer, `web/ai/panel.js`) and **New** (N: `web/ai/new-project.js`, "Create new project": Blank / Build with AI / Start from an example; Clear and Reset live there now). The drawer only ever edits: `edit {…, intent: "edit"}`; an answer of `mode: "new"` (or a whole plan that keeps fewer than half of the scene's items) changes nothing and the reply offers "Build it as a new scene…", which opens New → Build with AI with the same words. New → Build with AI sends `plan {text, observation?, images?, intent: "new"}` and never the scene. On an empty table the drawer builds through plan (intent "new"): there is nothing to keep. **Minimal change is enforced in the browser too:** every edit and check is solved with each untouched item (same entry as the base plan, and everything it rests on untouched) pinned to its exact pose, and its exact JSON is restored after the solve (byte for byte, same order; the table is widened about its middle instead of the content being shifted); an untouched item the change runs into is let go and moved the least the solver can, and the card says so. The card says "Edited: <scene>" or "New scene", lists exactly what changed and "Everything else is exactly as it was (N items untouched)", counted byte for byte (`report.edit.unchanged`). Regression tests: `web/ai/test/orchestrator.test.mjs` "starter: …" (the user's four requests).

### 13.9 The chat reply and next-edit chips (`reply`, `suggestions`: plan and edit)
The user asked for replies that are "more concise, intuitive, and helpful … like an eager assistant that makes the asked-for changes and suggests what it thinks would be a good edit". Both come in the same answer (no extra model call):
- **Where:** the step's `result` (the client reads `r.result`): **plan** → `result.reply`, `result.suggestions` (also on a plan answer with `intent: "edit"`: the change's reply and chips are copied there, and in `edit`); **edit** → the answer's top-level `reply` and `suggestions`, under every mode (an edit that went on to plan a new scene carries the new plan's reply and chips: `result.reply`, `result.suggestions`, and `result.plan.reply/suggestions`).
- **`reply`:** at most 2 short first-person sentences, plain words, real units the user would use, before → after where it helps ("I made the tennis ball lighter (58 g → 20 g) so the seesaw flings it farther."); never prop or item ids, field names or raw values. The validator collapses whitespace and keeps the first 2 sentences (a warning, never a repair turn); plan ≤ 400 characters, edit ≤ 1200.
- **`suggestions`:** 0–3 (the prompts ask for 2–3) `{label (≤ 6 words, ≤ 60 characters), prompt (the whole request as the user would type it, ≤ 300)}`: specific next edits of THIS scene (more reliable, more fun or dramatic, a natural next step), never generic. Tidied, never repaired: a plain string becomes both label and prompt, a longer label is cut to 6 words, duplicates and malformed ones dropped, at most 3; not a list → dropped.
- Old plans sent back (edit, refine) have their `reply`/`suggestions` left out of the prompt (they are the last turn's chat, not the scene).
- **browser** (a48d3b06a5b38e041's plan): the card's lead sentence is composed by the client from the real diff and the run's goal results; the step's `reply` shows under Details; the chips come from `suggestions` (the client puts its own "Fix it" first when a goal fails, and falls back to its own chips when none come).
- **Bench:** a soft `reply` check in `ai/bench/score.mjs` (in the score, never in pass): a reply is there, ≤ 2 sentences, no raw prop names / ids / raw values, 2–3 suggestions with labels ≤ 6 words whose prompts name something in the scene; the blinded judge gives a `chat` sub-score (0–10, not in its overall score). `run.mjs pipeline` records each build's `chat` {reply, suggestions}.
